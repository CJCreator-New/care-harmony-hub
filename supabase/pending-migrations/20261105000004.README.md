# 20261105000004: role-aware RLS (roadmap S0-04)

Issues: **DB-02** (P0), DB-07, DB-09, DB-13, DB-16, and reopened tickets 05 (invoices boundary) and 06 (active-user check). Depends on S0-01 (live baseline) and S0-03 (tenant key). Like every file in this folder, it is **not applied automatically**: see `README.md` here for promotion.

File: `20261105000004_role_aware_rls.sql`. Tests: `tests/s0-04/`.

## What it does

| Section | Change |
|---|---|
| **A. Helpers** | `STABLE SECURITY DEFINER` functions with `SET search_path = ''`, all new names: `my_staff_hospital_ids(roles[])`, `is_active_staff_of(hospital_id, roles[])`, `has_any_role(roles[], hospital_id)`, `my_patient_ids()`, `my_patient_hospital_ids()`, `is_patient_self(patient_id)`, `is_active_principal()`, `current_profile_id()`, `user_is_staff_of(user, hospital)`, `user_is_member_of(user, hospital)`, `profile_is_active(user)`, and parent lookups `patient_hospital_id`, `prescription_hospital_id`, `prescription_patient_id`, `invoice_hospital_id`, `invoice_patient_id`, `purchase_order_hospital_id`. A guard block aborts if any of these names already exists live with a different signature (the DB-03 failure mode), so `CREATE OR REPLACE` is safe. |
| **B. `user_belongs_to_hospital`** | Redefined with the **same** parameter names (`_user_id`, `_hospital_id`) to mean "active staff of that hospital". Every live policy that still calls it (outside the owned tables) stops matching patients and deactivated staff. This is the active-user fix that `20260909000001` intended and could not apply. |
| **C. Owned tables** | On 39 tables from `types.ts` plus `lab_queue` and `prescription_queue` (skipped if absent), **every permissive policy is backed up and dropped**, then the per-role, per-command policies in `rls_migration_audit.s004_policy_spec` are created (all `TO authenticated`, named `s004_<table>_<who>_<cmd>`). RESTRICTIVE policies (for example S0-10's `mfa_aal2_required`) are kept. If a table's new policies fail to compile (a column the live table lacks), that table keeps its old policies, a WARNING is raised and section E guards it. Also: a trigger makes `prescription_items.hospital_id` always equal the parent prescription's (DB-09), and one additive `s004_hospitals_patient_select` lets portal patients read their own hospital row. |
| **D. DB-13** | RLS is enabled on **every** `public` table that lacks it (extension-owned tables excepted). Known reference tables become read-only (`SELECT` for active principals, client writes revoked). Known PHI and ops tables get role-scoped policies when they have `hospital_id` or `patient_id`. Everything else is deny-by-default, with a WARNING per table. Partitions get RLS and no policy (they are read through the parent). |
| **E. Guard** | Every other table with RLS and someone else's permissive policy gets `s004_active_principal_guard`, a RESTRICTIVE `FOR ALL TO public` policy: `hospital_id IS NULL OR active staff of hospital_id OR own patient_id OR own user_id/sender_id/recipient_id`. PostgreSQL ANDs it with whatever the live policies say, so inactive users and patients lose hospital-wide access on tables nobody has rewritten yet. |
| **Bookkeeping** | Schema `rls_migration_audit` (not exposed by PostgREST, no grants to API roles): `s004_policy_spec` (the exact policy set), `s004_dropped_policies` (every dropped policy with `recreate_sql` and whether its name is in the repository history), `s004_repo_policy_names` (175 names found in `supabase/migrations/**`), `s004_run_log`. |

### Principals

| Principal | Definition | Gets |
|---|---|---|
| Active staff | a `user_roles` row with `role <> 'patient'` **and `hospital_id` = the row's hospital**, and a profile whose `is_active` is not `false` | the tables and commands its role needs (matrix below), in that hospital only |
| Patient | `patients.user_id = auth.uid()` and an active profile (the `patient` role row is **not** required, because `assign_patient_role` is broken, DB-15) | only rows of their own patient record(s), plus the scheduling directory of their hospital |
| Inactive | anyone else: no profile, `profiles.is_active = false`, staff whose roles were deleted (`DeactivateStaffDialog`), staff of another hospital, anon | nothing |

Membership comes from `user_roles.hospital_id`, not from `profiles.hospital_id` (user-writable until S0-03, DB-01). `profiles.is_active` is read through `to_jsonb`, so the helpers work whether or not the column exists live. A missing column or `NULL` counts as active.

Narrowing that further is a follow-up (row-level "minimum necessary").

## Operator steps

Never run any of this against production before the staging rehearsal.

1. **Prerequisites.** S0-01 capture exists; S0-03's `20261105000003_lock_tenant_key.sql` is applied or promoted together with this file (otherwise `user_roles` and `profiles.is_active` may still be user-writable, which weakens every check here). S0-10's `20261105000002` may be applied before or after; tests apply it first.
2. **Pre-flight.** Run the eight read-only queries in the `PRE-FLIGHT` block at the top of the SQL file against production (or the capture) and record the answers in the S0-04 ticket. Act on them:
   - query 3: staff role rows with `hospital_id IS NULL` lose all access. Backfill them (statement in the file) after checking each one;
   - query 6: portal users without a `patients.user_id` link see nothing;
   - query 7: `user_roles` must not be client-writable except by a hospital-scoped admin policy (S0-03). The repository's `"Admins can manage roles" FOR ALL USING (has_role(auth.uid(), 'admin'))` lets an admin of one hospital grant roles in another;
   - query 8: must return `_user_id uuid, _hospital_id uuid`.
3. **Dry run in abort mode** on a restored copy of production (or the S0-01 baseline replay):

   ```sql
   SET s0_04.unknown_policy_mode = 'abort';
   \i supabase/pending-migrations/20261105000004_role_aware_rls.sql
   ```

   It fails and changes nothing if an owned table carries a policy whose name is not in the repository history. For each one: either it is obsolete (rerun in the default sweep mode, which backs it up and drops it), or it expresses access the matrix lacks (add a policy to the spec, then rerun).
4. **Apply** (sweep mode, the default) on staging. Then review:

   ```sql
   SELECT section, action, tablename, detail FROM rls_migration_audit.s004_run_log ORDER BY id;
   SELECT tablename, policyname, cmd, in_repo_history FROM rls_migration_audit.s004_dropped_policies ORDER BY id;
   ```

   `failed_kept_old_policies` means a table did not match the expected columns: fix the spec for it. `closed_unclassified` lists tables that were wide open and are now deny-all: classify the ones clients need. `guarded` lists the tables still governed by unknown policies plus the guard: these are the next candidates for an explicit spec.
5. **Staging checks** with real JWTs (one user per role, a portal patient, a deactivated user, a user of a second hospital): repeat the read matrix of the local test through `/rest/v1/<table>?select=count`. In particular: a doctor gets `[]` from `invoices`; a receptionist of hospital A gets `[]` for hospital B; a patient sees exactly their own rows; a user deactivated through the UI gets `[]` everywhere on the next request.
6. **Promote** per `README.md`, then regenerate `src/integrations/supabase/types.ts` (new functions).
7. **Rollback** (if a critical workflow breaks and cannot wait for a policy fix):

   ```sql
   -- restore the dropped policies, then remove this file's policies
   DO $$ DECLARE r record; BEGIN
     FOR r IN SELECT DISTINCT ON (tablename, policyname) recreate_sql FROM rls_migration_audit.s004_dropped_policies
              ORDER BY tablename, policyname, id DESC LOOP EXECUTE r.recreate_sql; END LOOP;
     FOR r IN SELECT tablename, policyname FROM pg_policies WHERE schemaname = 'public' AND policyname LIKE 's004\_%' LOOP
       EXECUTE format('DROP POLICY %I ON public.%I', r.policyname, r.tablename); END LOOP;
   END $$;
   ```

   This reopens DB-02. Prefer adding one missing policy to the spec. `user_belongs_to_hospital` keeps its new meaning unless you recreate the old body explicitly, and RLS stays enabled on the DB-13 tables.

## Not covered here (follow-ups)

- **Storage** `documents` bucket policies use `profiles.hospital_id` folder checks (DB-17). Not in `public`, not touched.
- **Audit tables** (DB-08, S1-05): `activity_logs` gets only the section E guard. Its open insert and the partitions' creation function remain S1-05.
- `has_role(_user_id, _role)` is still global (not hospital-scoped); nothing in this file uses it.
- `get_user_hospital_id(_user_id)` is still callable for any user id.
- Helpers that describe *other* users (`user_is_member_of`, `patient_hospital_id`, …) are executable by `authenticated`, which lets a signed-in user test whether a known user/patient UUID belongs to a hospital. Low risk (UUIDs), noted for S1-08.
- Performance: the policies use uncorrelated `IN (SELECT helper())` subqueries, evaluated once per statement. Child tables call one indexed parent lookup per row. Make sure `user_roles(user_id)`, `patients(user_id)` and the parents' primary keys are indexed (they are in the repository schema).
- CI: S1-08 should run `tests/s0-04/run-tests.mjs` (or a pgTAP port) against the S0-01 baseline.
