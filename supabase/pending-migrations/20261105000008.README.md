# 20261105000008: audit trail integrity

Roadmap S1-05, issues DB-08, EDGE-09, DB-06. The migration
`20261105000008_audit_trail_integrity.sql` makes the audit tables append-only,
stops clients writing or reading audit rows across tenants, and hardens the
SECURITY DEFINER functions. Nothing has been applied to any database.

EDGE-09 is only partly addressed here. The audit-logger edge function is in
`supabase/functions/` and is outside this file's scope. See "Not fixed" below.

## What the migration does

| Section | Effect |
|---|---|
| A.0 | Creates `public.audit_reject_mutation()`, a trigger function that raises `insufficient_privilege` for UPDATE, DELETE or TRUNCATE. |
| A.1 | For each audit table that exists: a row trigger `trg_<table>_append_only` (BEFORE UPDATE OR DELETE) and a statement trigger `trg_<table>_no_truncate` (BEFORE TRUNCATE) on the table and on every partition. RLS is enabled on each. UPDATE, DELETE and TRUNCATE are revoked from PUBLIC, `anon` and `authenticated`. `service_role` is not revoked, but the triggers still stop it, because triggers apply to every role. |
| B | Drops every INSERT and FOR ALL policy on `activity_logs`, `audit_logs`, `audit_log`, `prescription_audit`, `invoice_adjustment_audit` and `lab_result_audit`, whatever its name. Creates one self-bound INSERT policy per table where the columns allow it (see the matrix). |
| C | Drops every SELECT and FOR ALL policy on `activity_logs` and `audit_logs`. Creates admin reads limited to the admin's own hospital, and self reads where `user_id` exists. `audit_log_summary` gets `security_invoker = true`. |
| D | Revokes EXECUTE on `log_audit_event`, `create_amendment_audit` and `set_audit_context` from PUBLIC, `anon` and `authenticated`. No migration or `src/` file calls them. |
| E | Sets `search_path = public, pg_temp` on every SECURITY DEFINER function in `public` that has none. Extension-owned functions are skipped. |

No row is read, changed or deleted. Every section skips an absent table or
column.

## Why each change is needed (live state)

The validation fixture `supabase/pending-migrations/tests/consolidated-bundle/00000000000000_fixture.sql`
is the live policy export, and it shows the problems this file removes:

| Table | Live policy (from the export) | Problem |
|---|---|---|
| `activity_logs` | `Staff can insert activity logs` INSERT, TO public, `WITH CHECK (true)` | Any caller, including `anon`, can insert any row. |
| `activity_logs` | `activity_logs_self_insert` INSERT, TO public, `WITH CHECK (true)` | Same. |
| `activity_logs` | Four SELECT policies, all `USING (true)` in the export | Any staff member reads the whole trail. |
| `audit_logs` | `audit_logs_authenticated_insert` INSERT, `WITH CHECK (true)` | Any caller inserts any row. The 20260909000001 version was `user_id IS NULL OR user_id = auth.uid()`, which still allows anonymous rows. |
| `audit_logs` | `audit_logs_hospital_admin_read` SELECT, `USING (true)` | Cross-tenant read of the audit trail. |
| `audit_logs` | `Admin can view all audit logs` (20260204000008), `Admins can view audit logs` (20260204000011): role check only, no hospital | Cross-tenant admin read in the migration history. Not in the export, but dropped here whatever the live set is. |
| `audit_log_summary` (view) | no `security_invoker` | The view runs as its owner and reads `audit_log` past RLS. |
| `prescription_audit`, `invoice_adjustment_audit`, `lab_result_audit` | INSERT checks only `hospital_id IN (caller's hospitals)` | A staff member can write rows naming any actor. |

The export has no `user_id` column on `audit_logs`. In that case the migration
creates no client INSERT policy and no self-read policy for it. Only admin reads
by hospital remain. That is the safe default, but it means the client can no
longer write `audit_logs` (see "Client impact").

## Policy matrix after the migration

Roles are the `app_role` values. "Active" means the caller's profile is not
deactivated.

| Table | INSERT | SELECT | UPDATE / DELETE / TRUNCATE |
|---|---|---|---|
| `audit_log` | `audit_log_insert_as_actor`: `actor_user_id` is the caller's profile id and `hospital_id` is the caller's hospital | unchanged (20260313000001: any staff member, own hospital) | none for any role (trigger, revoke) |
| `prescription_audit`, `invoice_adjustment_audit`, `lab_result_audit` | `<table>_insert_as_actor`, same rule | unchanged (hospital scoped) | none |
| `audit_logs` | `audit_logs_self_insert`: `user_id = auth.uid()`, caller's hospital (only if `user_id` exists) | `audit_logs_admin_hospital_read`: admin of that row's hospital, active; `audit_logs_self_read`: `user_id = auth.uid()` (only if `user_id` exists) | none |
| `activity_logs` | `activity_logs_self_insert`: `user_id = auth.uid()` and (`hospital_id` NULL or the caller's hospital) | `activity_logs_admin_hospital_read`: admin of that hospital; `activity_logs_self_read`: `user_id = auth.uid()` | none |
| `admin_activity_logs` (if present) | not changed by this file | not changed | none (append-only trigger from A.1 only) |

`anon` gets nothing on any of these tables. Edge functions use the service role
and are not affected by the policies.

## Client impact (check before promoting)

1. `src/modules/order-safety/adapters/SupabaseAdapters.ts` (`logSafetyEvent`,
   around line 191) inserts into `audit_logs` with `performed_by` and no
   `user_id`. After this migration that insert is refused. Its events must go
   through a server path (an edge function with the service role, or a
   SECURITY DEFINER function that takes the actor from `auth.uid()`). That is
   the S1-05 design, and it needs a `src/` change.
2. The `activity_logs` inserts in `src/hooks/` were checked for `useAudit`,
   `useQueue` and `useLabOrders`: they set `user_id` to the session user id
   (`auth.uid()`) and keep working. `useConsultations` and `useRefillRequests`
   were not checked. Before promoting, confirm that every `activity_logs`
   insert sets `user_id` to `auth.uid()`. A row with another `user_id`, or with
   a `hospital_id` the caller does not belong to, is now refused.
3. `activity_logs` is not write-once for the owner of a row. A signed-in user
   can still write any `action_type` and `details` for their own `user_id`.
   Removing that needs server-only writes (item 1 of "Not fixed").
4. Admin pages that read `audit_logs` or `activity_logs` across hospitals will
   now see only their own hospital. That is intended.

## Not fixed here

- **EDGE-09** (`supabase/functions/audit-logger/index.ts`): the function accepts
  caller-supplied events and exposes the trail to every staff role. It is in
  `supabase/functions/`, outside this file's scope. The edge change should set
  the actor from the verified JWT and read only the caller's hospital.
- **Server-only writes.** The DoD is "no client can insert arbitrary audit
  rows". Clients may still write their own `activity_logs` rows (item 3 above).
  Full closure needs a `log_event` SECURITY DEFINER function (actor from
  `auth.uid()`), triggers on the PHI tables, and `src/` to stop writing
  directly. That is a code change, not a migration.
- **Parallel audit stores (DB-08).** `audit_log`, `audit_logs` and `activity_logs`
  coexist. Consolidating them is a separate task.
- **Partition retention.** Partitions can be detached and archived by a
  superuser maintenance task, as the 20260622000003 comment describes. The
  triggers do not block `DETACH PARTITION` or `DROP` by a superuser.
- **Policy-by-policy review of other audit writers.** Rows written by triggers
  that run as the owner (the SECURITY DEFINER functions in 20260313000002 and
  20260313000003) are not affected by client policies.

## Validation performed (2026-11-05)

- Replay with `scripts/db/replay-migrations.mjs --stop-on-error` on the
  validation fixture (`tests/consolidated-bundle`, text and date variants),
  followed by a second application of the same file under a new version. Both
  pass.
- Behavioural checks run in rolled-back transactions on a scratch PostgreSQL
  16 cluster (41 checks in one suite, 14 in a live-shaped suite, 6 on a
  partitioned `activity_logs`, and 2 on a simulated `prescription_audit`). They
  covered: UPDATE, DELETE and TRUNCATE rejected for the owner and for
  `authenticated`; open insert and read policies removed; cross-tenant admin
  reads and forged rows refused; self-writes still allowed; `security_invoker`
  set; `search_path` set on every public SECURITY DEFINER function.
- Not run: the full `supabase/migrations/` history. On this cluster it applies
  10 of 64 files and fails on the rest, which is the known S0-01 state, not a
  regression from this file.
