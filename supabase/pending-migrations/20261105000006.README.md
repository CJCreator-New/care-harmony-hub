# 20261105000006: RLS for the six lab tables

Urgent exposure: `lab_results`, `lab_qc_results`, `lab_trends`,
`lab_interpretation_rules`, `critical_value_notifications` and `loinc_codes`
have row-level security off in production. The migration
`20261105000006_rls_lab_tables.sql` adds deny-by-default policies and then
enables RLS. Nothing has been applied to any database.

## Policy matrix

Roles are the `app_role` values. "Active" means a `user_roles` row for the
hospital plus a profile that is not deactivated. Tenant rows match when their
hospital is one of the caller's hospitals for the listed roles.

| Table | Operation | Roles allowed | Hospital rule |
|---|---|---|---|
| `lab_results` | SELECT | admin, doctor, nurse, lab_technician | parent `lab_orders.hospital_id` when linked, else own `hospital_id` |
| `lab_results` | INSERT, UPDATE | doctor, lab_technician | same; a row whose `hospital_id` differs from its order is refused |
| `lab_results` | DELETE | none | |
| `lab_qc_results` | SELECT | admin, lab_technician | own `hospital_id` |
| `lab_qc_results` | INSERT, UPDATE | lab_technician | own `hospital_id` |
| `lab_qc_results` | DELETE | none | |
| `lab_trends` | SELECT | admin, doctor, nurse, lab_technician | own `hospital_id` |
| `lab_trends` | INSERT, UPDATE | doctor, lab_technician | own `hospital_id` |
| `lab_trends` | DELETE | none | |
| `critical_value_notifications` | SELECT | admin, doctor, nurse, lab_technician | own `hospital_id` |
| `critical_value_notifications` | INSERT | doctor, lab_technician | own `hospital_id` |
| `critical_value_notifications` | UPDATE (acknowledge, escalate) | doctor, nurse, lab_technician | own `hospital_id` |
| `critical_value_notifications` | DELETE | none | |
| `loinc_codes` | SELECT | any authenticated user | none (reference) |
| `loinc_codes` | INSERT, UPDATE, DELETE | active admin (any hospital) | none (reference) |
| `lab_interpretation_rules` | SELECT | any authenticated user | none (reference) |
| `lab_interpretation_rules` | INSERT, UPDATE, DELETE | active admin (any hospital) | none (reference) |
| all six | any | patient, receptionist, pharmacist, anon | no policy, so no access |

Restrictive policies on these tables (for example the aal2 guard from
`20261105000002`, if applied) are not dropped and still apply in addition.

## Helper functions

All are `SECURITY DEFINER` with `SET search_path = ''`. Execute rights go to
`authenticated` only where a policy calls them. `anon` and `PUBLIC` get none.

- `public.lab_rls_profile_active(uuid)`: profile not deactivated. Internal.
- `public.lab_rls_staff_hospital_ids(text[])`: hospitals where the caller is
  active staff with one of the listed roles. Internal.
- `public.lab_rls_can_access(text[], uuid)`: the hospital is one of those.
- `public.lab_rls_result_access(text[], uuid, uuid)`: `lab_results` version
  that uses the parent order's hospital.
- `public.lab_rls_is_active_admin()`: active admin in any hospital.

The role lookup follows `20261105000004_role_aware_rls.sql`. It reads
`user_roles` and `profiles` directly, so this file does not depend on that
file's helpers and runs whether or not it has been applied.

## Hospital scoping, by table

- `lab_results` has a nullable `hospital_id` and no `patient_id`. Scope comes
  from the parent `lab_orders` row (`lab_order_id`), which has a non-null
  `hospital_id`. Rows without an order use their own `hospital_id`. Rows with
  neither are visible to nobody.
- `lab_qc_results`, `lab_trends`, `critical_value_notifications` each have a
  nullable `hospital_id`, and it is used directly. A NULL value makes the row
  invisible to everyone, admin included.
- `lab_trends` has `patient_id`, `critical_value_notifications` has `patient_id`
  and `lab_result_id`. These are not used for scoping; the hospital is the tenant.
- `loinc_codes` and `lab_interpretation_rules` have no hospital column. They are
  global reference data.

## Existing code that this migration does not fix

These are outside the scope of an RLS change. Each one is listed so it is not
mistaken for a regression.

1. `useLaboratory.ts` `calculateTrend` inserts `hospital_id: 'current'`. That is
   not a UUID, so the insert fails with or without this migration.
2. `useLaboratory.ts` `addLabResult` and `createCriticalValueNotification`
   write to `critical_value_alerts`, which is not one of the six tables. Its
   RLS is not covered here.
3. `supabase/functions/fhir-integration` selects `patient_id` from
   `lab_results`, which the live types do not have. It runs on the service role,
   so RLS does not affect it, but the query will fail at runtime.
4. The rule for `critical_value_notifications` UPDATE includes `nurse`. No client
   writes this table today. If the nurse read-back workflow is built, this
   grant is the one it will use.
5. The patient role has `LAB_READ` in `rbac.ts`, but no patient-facing code path
   reads these six tables, so patients get no policy. If a patient lab view is
   added, add a policy keyed on the patient's own `patients` row, not a hospital
   list.

## Interaction with other pending migrations

- `20261105000004_role_aware_rls.sql` classifies `lab_interpretation_rules` as
  reference data. Its section D skips tables that already have foreign permissive
  policies, so the two files do not conflict in either order. Each one replaces
  permissive policies on these tables.
- `20261105000002_mfa_backup_codes_and_aal2.sql` adds a restrictive aal2 policy
  to PHI tables; this file keeps restrictive policies, so the MFA guard still
  applies to whatever it targets.
- Earlier migrations `20260204000011_misc.sql` and
  `20260309000003_pharmacy_lab_portal_rls.sql` already had policies (some
  permissive, some `FOR ALL`) and `ENABLE ROW LEVEL SECURITY` on some of these
  tables. The file drops every permissive policy on the six tables first so
  none of them widen access.
