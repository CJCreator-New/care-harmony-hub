### Patient self-registration rule

A patient claims the record that staff already created. The claim needs all of these:

- the hospital code (`hospitals.license_number`);
- the MRN;
- the date of birth;
- the last name;
- the **email address on the record**.

The hospital comes from the matched record, never from the request. The account is created unconfirmed, so the confirmation email proves the caller owns the record's email. A record without an email cannot be claimed: reception adds the email first.

Throttling, per hour: 10 failures per client (hashed IP), 5 per (hospital, MRN), and 50 per hospital.

A patient's profile gets `hospital_id` = the record's hospital and `is_staff = false`, so the portal keeps working (it reads `hospital` from the profile). Under today's hospital-membership RLS, that also gives the patient hospital-wide reads. This is the existing DB-02 exposure for every patient account, and it is fixed by **S0-04** (role-aware RLS), not here. What changes in S0-03 is that a patient can no longer pick the hospital.

## Application changes (same commit series)

| Component | Now |
|---|---|
| `supabase/functions/register-patient` (new) | Anonymous POST `{ email, password, hospitalCode, mrn, dateOfBirth, lastName }`. It calls `verify_patient_claim`, then `auth.admin.createUser` (unconfirmed), then `register_patient`. If that fails, it deletes the new auth user (FUNC-01: no orphaned accounts). Finally it calls `auth.resend({ type: 'signup' })`. Pure logic is in `_shared/onboarding.ts` (tests: `tests/security/onboarding.test.ts`). |
| `supabase/functions/create-hospital-admin` | No longer requires the `admin` role. A brand-new account cannot have that role, so hospital sign-up used to be refused. It now uses the caller's JWT identity, and the RPC enforces "no hospital, no role". RPC errors map to 409/404/400 instead of 500. |
| `supabase/functions/accept-invitation-signup` | Unchanged. It already passes the invited email, and the hardened RPC checks it. |
| `src/pages/patient/PatientRegisterPage.tsx` | 3 steps (record, account, confirm). It calls only `register-patient`. The security question, the hospital lookup, the profile update, `rpc('register_patient')` and the client `signUp` are all removed. The medical-info step is removed too: staff own the clinical record. |
| `src/components/admin/AdminRepairTool.tsx` | Uses `createHospitalAndProfile` (`create-hospital-admin`) for an account with no hospital. An account with a hospital but no admin role gets a message to ask an admin; client role inserts are no longer allowed. |
| `src/routes/routeDefinitions.tsx` | `/hospital/role-setup` is admin-only (SECF-09). |

Edge functions cannot be run under Deno in this environment. The SQL and the pure helpers are tested; the function wiring needs the staging check below.

## Deployment order

Pushing to `main` deploys edge functions and the client through Lovable. This migration stays pending until S0-01 is done.

1. **`20261105000002` and this file together**, in that order, after S0-01. This file aborts without `20261105000002`.
2. **`create-hospital-admin`: do not deploy before the migration.** The old `create_hospital_with_admin` moves any caller's profile to the new hospital. With the role check removed, any member (a nurse of hospital A, for example) could create an empty hospital, become its admin and leave A. They gain no access to existing data, but `has_role(uid, 'admin')` is not tenant-scoped in some live policies. Either hold this function change until the migration is live, or ship it in the same release.
3. **`register-patient` and `PatientRegisterPage`** fail closed without the migration. `verify_patient_claim` is missing, so the user sees "Registration failed" (500). Self-registration is already broken today (FUNC-01), so deploying them early changes nothing, but keep them in the same release.
4. **After the migration, an old client breaks** where it writes `security_question`/`security_answer`, sets `hospital_id` (old `PatientRegisterPage`, old `AdminRepairTool`) or self-inserts `user_roles`. All of those are replaced in this series. Ship the client before the migration, or together with it.
5. **Regenerate `src/integrations/supabase/types.ts`** after applying. The `profiles` security and legacy 2FA columns disappear, and the new RPCs appear.

## Operator steps

1. **Auth settings.** Enable *Confirm email* (Authentication → Providers → Email). Patient registration relies on it to prove the caller owns the record's email. If it is off, `createUser(email_confirm: false)` accounts may be able to sign in before confirming, depending on the Auth version. Check this in staging.
2. **Data check before promoting** (read-only):
   ```sql
   select count(*) filter (where email is null) as no_email, count(*) as total
     from public.patients where user_id is null;            -- records patients cannot claim yet
   select count(*) from public.hospitals where license_number is null;  -- hospitals with no code
   select count(*) from public.profiles where security_answer is not null;
   ```
   Hospitals without a `license_number` have no hospital code. An admin sets one in hospital settings.
3. **Reconcile against the S0-01 capture.** Check the live policy names on `profiles`, `user_roles` and `staff_invitations`. Drop any extra permissive INSERT/UPDATE policy on `profiles` or `user_roles` that lets a user write their own row. Also check that `staff_invitations.token` compares as text, and that no view depends on the dropped columns (the migration warns if one does).
4. **After review, drop the archives** if they are not wanted: `drop table public.profiles_legacy_2fa_archive;`. The same applies to `public.profile_security_answers` if the product drops security questions for good. Nothing reads either table.
5. **Staging check:**
   - As any user, `PATCH /rest/v1/profiles?user_id=eq.<self>` with `{"hospital_id":"<other>"}` returns 403.
   - `GET /rest/v1/profiles?select=security_answer` returns 400 (no such column).
   - `POST /rest/v1/user_roles` with `{"user_id":"<self>","role":"admin"}` returns 403.
   - As a nurse, `POST /rest/v1/staff_invitations` returns 403.
   - `POST /rest/v1/rpc/register_patient` with a user JWT returns 403/404.
   - Sign up a new hospital through `/hospital/signup`: you reach `/hospital/role-setup` as admin.
   - Create a patient at reception with your test email, then register at `/patient-register` with its MRN/DOB/last name. You get the confirmation email, can sign in at `/patient-login` and see only that record.
   - A wrong DOB returns 400. Five wrong DOBs for one MRN return 429.
