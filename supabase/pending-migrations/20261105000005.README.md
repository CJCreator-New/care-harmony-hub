This note covers the pending migration and the code changes made with it. The shared `README.md` in this folder explains how pending migrations are promoted. Nothing here is applied automatically.

## Operator steps

Never commit secrets or production data while doing these.

1. **Undeploy `backup-manager`.** Deploying this branch replaces the live code with the 410 stub. Then delete the function: `npx supabase functions delete backup-manager --project-ref <ref>`. Removing the directory from the repository does not undeploy a function, so the stub stays in the repository until the deletion is confirmed.
2. **Inspect what it left behind.** The function wrote JSON dumps of whole tables, across all tenants, to the storage bucket `backups`, and job rows to `backup_jobs` and `backup_schedules`. Review the bucket's contents and access policies. Treat any object there as a possible cross-tenant PHI export (check the storage logs for who triggered `create_backup`, and whether `restore_backup` ever ran). Then delete the objects and make the bucket private or remove it, following your incident and retention policy.
3. **Confirm point-in-time recovery** is enabled on the project (S5-02). It is now the only backup path.
4. **Apply the migration** (after S0-01, as described in `README.md`), or run it directly in the SQL editor if the purge function must be closed before then. It is idempotent and has no prerequisites. Afterwards, `select proname from pg_proc where proname in ('purge_old_audit_logs_staging_only','test_setup_prescription_audit_scenario','test_setup_invoice_audit_scenario');` must return no rows, and `POST /rest/v1/rpc/purge_old_audit_logs_staging_only` must return 404.
5. **Check the audit trail for past use.** Compare `audit_log` row counts and the earliest `event_time` against backups. A gap may mean the purge was called. Also look for audit rows with the fixed fixture ids `a0000000-0000-0000-0000-000000000001` (hospital) and `b0000000-…-0001` (patient) written by the `test_setup_*` helpers.
6. **FHIR SMART scopes.** Any integration that relied on a `scope` in `user_metadata` or on `system/*` scopes now gets 403 unless the user also has a fallback role (admin, doctor, and so on) in the patient's hospital. Grant scopes only through `app_metadata` (service role). A real backend `system/*` client needs a separate service-token path; none exists yet.
7. **DB-11 data review.** Data corrupted by the old migrations is not repaired by this change. Compare against a backup taken before 2026-02-21 / 2026-03-28: patients whose `gender` was rewritten by first name, MRNs that were truncated by `LPAD`, deleted patients whose names contained "Creator" (and their cascaded records), and de-duplicated consultations and queue rows.

## Not done here (owned elsewhere)

- `fhir-integration` still uses the shared `authorize()` gate before its own actor check; moving every function to one actor helper is **S0-06**. Error bodies that echo database messages in `fhir-integration` are EDGE-21 (**S2-07**).
- `20260204000011_misc.sql` sets `profiles.is_active = true` for every profile whose `clearance_level` is NULL while backfilling the clearance level. On an existing database that could re-activate deactivated accounts. It is listed as reviewed in the DB-11 test so the test passes, but should be checked against the live data in **S0-01**.
