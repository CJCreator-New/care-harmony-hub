# Consolidated SQL bundle (pending migrations S0-03 to S2-08)

One paste-in-order bundle for the eight files in `supabase/pending-migrations/` (`20261105000001` to `…000009`, with `…000003` tied to the `…000002` prerequisite). It brings the database in line with the code on `main`. Everything here is generated by `scripts/db/build-consolidated.mjs` from the source migrations, which are copied verbatim. Do not edit these files by hand. Change the source, or change the generator, and run it again.

## Status: validated on a scratch database, not on the live project

- **Validated:** all 11 parts apply in order on PostgreSQL 16 against the validation fixture, then `99-verify.sql` returns 98 of 98 `ok`. A second pass of every part on the same database also exits 0 and verify stays 98 of 98. Both fixture variants (text and date `patients.date_of_birth`) pass.
- **Not validated:** the live schema. The S0-01 baseline does not exist yet, and the repository migration history cannot replay on its own (10 of 64 files). Run `00-preflight.sql` on the live project before anything else, and read every row.
- **Parts 02, 04 to 06 and 07 to 09 change access for real users.** Each carries a GATE line in its header. Read it before pasting.
- **Parts 07, 08 and 09 need app changes first.** Parts 07 and 08 make client writes fail that the app makes today. See their GATE lines and the migration READMEs.

## How to run it in the Lovable SQL editor

1. Take a restore point first (point-in-time recovery or a fresh backup). Only S0-04 has a rollback script (see Rollback).
2. Run `00-preflight.sql` by itself. Read every row. Stop and resolve before going on if:
   - `supabase_migrations versions 20261105%` lists versions that already ran, or the drizzle history shows the same objects (drizzle 0018 and 0020 touch `profiles`, `role_requires_2fa` and `user_belongs_to_hospital`, which overlap parts 02 and 04);
   - `user_belongs_to_hospital arguments` is not `_user_id uuid, _hospital_id uuid` (S0-04 cannot redefine it otherwise);
   - the `profiles legacy and privileged columns` row shows what S0-03 will remove;
   - the `discharge_workflows` row does not have `status`, `current_step` and `initiated_by` (part 09 stops if they are missing). The repository has two definitions of this table (`20260311000003` and `tier4_1`); the live one decides.
3. Before part 02, do the S0-10 steps in `supabase/pending-migrations/README.md` (the `20261105000002` section). Set `BACKUP_CODE_PEPPER`, enable TOTP in Auth, and make sure every admin and doctor can enrol a factor. Part 02 will lock them out of PHI tables until they do.
4. Before part 04, do the steps in `20261105000004.README.md` (steps 2 and 3): the pre-flight queries, the review of the policies that part 04's preflight lists, and a dry run on a restored copy. The abort guard is the default: if any listed policy is not on the reviewed list, part 04 raises and rolls back. The bundle never sets sweep mode.
5. Before part 09, ship the app changes its GATE line names. Before part 10, ship the telemedicine upload path, the `logSafetyEvent` user id and the admin-only document delete. Before part 11, ship the telemedicine and document-delete changes. The migration READMEs list them.
6. Paste one part at a time, in order, `part-01` through `part-11`. Read each part's header. It names the check to make after that part. Do not skip a part, and do not run them out of order.
7. If a part shows an ERROR, stop there. If the editor left a transaction open, run `ROLLBACK;`. Wrapped parts (01, 02, 03, 04 (first third), 07, 08, 09, 10, 11) roll back as a whole. Parts 05 and 06 do not: a failure in part 05 leaves part 04 applied.
8. Run `99-verify.sql`. Every row must read `ok`. A `MISSING` row is a finding: read its `detail` column, then the matching part note in this README or the migration README. Do not work around it.
9. Re-running the bundle is not a no-op for S0-04 (Known risks, item 4). Run it once.

## What it changes for users

- **Roles and profiles (S0-03).** Clients can no longer write `profiles.hospital_id`, `is_active`, `is_staff`, `role`, the 2FA columns or the lockout columns; the guard trigger rejects it. Clients can no longer insert their own `user_roles` rows. Self-registration for patients goes through the `register-patient` edge function. Security questions and answers are gone from `profiles`.
- **MFA (S0-10).** Admins and doctors need an `aal2` session (Supabase MFA factor) to read or write patients, consultations, prescriptions, prescription items, lab orders, vital signs and medical records. At `aal1` they see zero rows. Backup codes are generated server-side. The old custom TOTP edge functions return 410.
- **Role-aware RLS (S0-04).** Each role sees only its own hospital's rows and its own patient's rows. Deactivated staff lose access. Invoices and payments are admin and receptionist only. Several client screens will return empty results or fail (the list is in `20261105000004.README.md`, "Known client features that break"). Patients lose the direct edit of their demographics.
- **Lab tables (S0-06).** The six lab tables become deny-by-default. Only the roles in the policy matrix (`20261105000006.README.md`) can read or write them.
- **Destructive endpoints (S0-05).** The purge and test-setup RPCs are gone. The `backup-manager` edge function returns 410 (its own README covers undeploying it).
- **Critical lab escalation (S0-08).** The escalation worker runs only after the operator steps are done (`pending-migrations/README.md`, step 3). Until then, alerts are written but nobody is paged by the database.
- **Prescriptions and discharge (S1-02).** Prescription approval is pharmacist-only for end users. Dispensing from `pending` is refused. The app paths that still do either fail after part 09 (`PrescriptionDispensingEngine`, `usePrescriptions` dispense, admin approve in the client state machine).
- **Audit trail (S1-05).** Audit rows cannot be updated, deleted or truncated by client roles. Client-side audit writes must set the acting user.
- **Patient, appointment and consultation deletes (S2-08).** Hard DELETE is refused; use the soft-delete path. Parent deletes that cascaded to PHI children now stop with RESTRICT.

## Rollback

- **S0-04 only.** `20261105000004.README.md`, step 7, has the rollback SQL. It restores the dropped policies from `rls_migration_audit.s004_dropped_policies` and removes the `s004_%` policies. It reopens DB-02 while it is in place.
- **Everything else.** Their READMEs contain no rollback SQL. The only recovery is the restore point from step 1. Some changes are not reversible by SQL: S0-03 drops the security-answer and legacy-2FA columns, S0-05 drops the RPCs, and S2-08 may drop unused log rows only through an explicit purge call. Their data is gone unless the restore point has it.

## Known risks

1. **S0-03 date comparison (fixed in source).** `20261105000003_lock_tenant_key.sql` compared `p.date_of_birth` with a `date` parameter. The source now calls `patient_dob_as_date()`, which has a text overload (NULL for anything that is not a valid YYYY-MM-DD) and a DATE overload. The comparison works for either column type. `src/integrations/supabase/types.ts` shows `string` for `date`, `timestamptz` and `text` alike, so it cannot tell the live type; the repository migrations declare `patients.date_of_birth DATE NOT NULL`. Validated on a text-typed and a date-typed fixture.
2. **Live schema not captured.** Everything here was written from repo files and the generated types. The S0-01 baseline and the `live_*.tsv` captures do not exist yet. Column types, policy names, RLS state and the `discharge_workflows` definition may differ on the live database. Part 04 and part 09 are the most sensitive to this.
3. **S0-04 reviewed-name list.** Part 04 aborts by default if a permissive policy on an owned table is not on the reviewed list. On the validation fixture the list matches and part 04 completes. The live project will differ, so the preflight output decides. The 64 names and their history are in `20261105000004.README.md`, step 3.
4. **S0-04 is not idempotent.** A full second run adds `s004_active_principal_guard` (RESTRICTIVE) on `lab_qc_results` and `lab_trends`, because S0-06 creates the permissive policies after S0-04 runs. The added guard only narrows access to active staff. The second-pass run on the fixture exits 0 and verify stays 98 of 98, but the schema was not diffed after the second pass, so this is not re-measured. Fixing it means changing the source.
5. **Parts 05 and 06 are not transactions.** A failure in part 05 or 06 leaves S0-04 partly applied. Recovery is the restore point, or the rollback in S0-04's README.
6. **Session-local helpers.** S0-04 defines `pg_temp.s004_staff` and `pg_temp.s004_self` and uses them later. Parts run in separate sessions, so the generator copies those two definitions into parts 05 and 06 as labelled "session prelude" blocks.
7. **Editor transaction behaviour is unknown.** If the Lovable editor wraps each paste in its own transaction, a `BEGIN;` inside a wrapped part is a warning and its `COMMIT;` ends the editor's transaction early. Check the first wrapped part's result before continuing.
8. **Verify checks shape, not behaviour.** `99-verify.sql` checks that objects exist, RLS is on, the trigger exists, the signature matches, and the columns are gone. It does not check who can read what. The behaviour matrices in `tests/` have not been run against this bundle on the live database.
9. **Validation fixture is a stand-in.** It is the union of the test fixtures plus the `types.ts` tables. Its `auth.users` rows are a small set, not real Supabase Auth. It has no pg_cron, pg_net or Vault, and no Supabase policies beyond the fixture's. Its `discharge_workflows` and `prescription_approval_workflows` tables were replaced with the column shapes from the repository (base-only: NOT NULL and FK constraints relaxed, because the fixture inserts partial rows). The fixture is in `supabase/pending-migrations/tests/consolidated-bundle/`.
10. **Lab screens.** Part 08 makes six lab tables deny-by-default. `20261105000006.README.md` lists existing client issues it does not fix, including `calculateTrend` inserting `hospital_id: 'current'`, which is not a UUID.
11. **Secrets are not in the bundle.** The pepper, the Vault secrets, the edge-function secrets and the Auth settings are operator steps in the migration READMEs. Part 02 and part 01's worker need them.
12. **Verify does not check the audit and state-machine behaviour.** Parts 09 to 11 are checked for object existence only. Their transition and append-only behaviour was tested in the migration validation runs, not in this bundle's verify.
