# Consolidated SQL bundle (pending migrations S0-03 to S0-10)

One paste-in-order bundle for the six files in `supabase/pending-migrations/`. It brings the database in line with the code on `main`. Everything here is generated by `scripts/db/build-consolidated.mjs` from the source migrations, which are copied verbatim. Do not edit these files by hand. Change the source, or change the generator, and run it again.

## Status: not ready. Do not paste into a live database

- **Part 03 (S0-03) applies** on a text-typed and on a date-typed `patients.date_of_birth` (source fix, Known risks, item 1).
- **Part 04 (S0-04) stops on the validation fixture.** Abort is the default, and the guard raises on 64 policy names on the owned tables that are not on the reviewed list. Nothing in part 04 changes when it raises (Known risks, item 3). Review those names first, then decide. Parts 05 to 08 and the end-to-end verify have not run to completion on the fixture.
- **Parts 02 and 04 to 06 change access for real users** (MFA enforcement, role-aware RLS). Each carries a GATE line in its header. Read it before pasting.
- **Nothing was checked against a live capture.** The S0-01 baseline does not exist yet.

## How to run it in the Lovable SQL editor

1. Take a restore point first (point-in-time recovery or a fresh backup). Nothing here has a rollback script except S0-04 (see Rollback).
2. Run `00-preflight.sql` by itself. Read every row. Stop and resolve before going on if:
   - `supabase_migrations versions 20261105%` lists versions that already ran, or the drizzle history shows the same objects (drizzle 0018 and 0020 touch `profiles`, `role_requires_2fa` and `user_belongs_to_hospital`, which overlap parts 02 and 04);
   - `user_belongs_to_hospital arguments` is not `_user_id uuid, _hospital_id uuid` (S0-04 cannot redefine it otherwise);
   - the `profiles legacy and privileged columns` row shows what S0-03 will remove.
3. Before part 02, do the S0-10 steps in `supabase/pending-migrations/README.md` (the `20261105000002` section: deployment order and operator steps). Set `BACKUP_CODE_PEPPER`, enable TOTP in Auth, and make sure every admin and doctor can enrol a factor. Part 02 will lock them out of PHI tables until they do.
4. Before part 04, do the steps in `20261105000004.README.md` (steps 2 and 3): the pre-flight queries, the review of the policies that part 04's preflight lists, and a dry run on a restored copy. Part 04 begins with that preflight. The abort guard is the default: if any listed policy is not on the reviewed list, part 04 raises and rolls back. The bundle never sets sweep mode.
5. Paste one part at a time, in order: `part-01`, then `part-02`, and so on through `part-08`. Read each part's header. It names the check to make after that part. Do not skip a part, and do not run them out of order.
6. If a part shows an ERROR, stop there. If the editor left a transaction open, run `ROLLBACK;`. Wrapped parts (01, 02, 03, 04 (first third), 07, 08) roll back as a whole. Parts 05 and 06 do not: a failure in part 05 leaves part 04 applied.
7. Run `99-verify.sql`. Every row must read `ok`. A `MISSING` row is a finding: read its `detail` column, then the matching part note in this README or the migration README. Do not work around it.
8. Re-running the bundle is not a no-op (Known risks, item 4). Run it once.

## What it changes for users

- **Roles and profiles (S0-03).** Clients can no longer write `profiles.hospital_id`, `is_active`, `is_staff`, `role`, the 2FA columns or the lockout columns; the guard trigger rejects it. Clients can no longer insert their own `user_roles` rows. Self-registration for patients goes through the `register-patient` edge function. Security questions and answers are gone from `profiles`.
- **MFA (S0-10).** Admins and doctors need an `aal2` session (Supabase MFA factor) to read or write patients, consultations, prescriptions, prescription items, lab orders, vital signs and medical records. At `aal1` they see zero rows. Backup codes are generated server-side. The old custom TOTP edge functions return 410.
- **Role-aware RLS (S0-04).** Each role sees only its own hospital's rows and its own patient's rows. Deactivated staff lose access. Invoices and payments are admin and receptionist only. Several client screens will return empty results or fail (the list is in `20261105000004.README.md`, "Known client features that break"). Patients lose the direct edit of their demographics.
- **Lab tables (S0-06).** The six lab tables become deny-by-default. Only the roles in the policy matrix (`20261105000006.README.md`) can read or write them. Patients and anonymous users get nothing from them.
- **Destructive endpoints (S0-05).** The purge and test-setup RPCs are gone. The `backup-manager` edge function returns 410 (its own README covers undeploying it).
- **Critical lab escalation (S0-08).** The escalation worker runs only after the operator steps are done (`pending-migrations/README.md`, step 3). Until then, alerts are written but nobody is paged by the database.

## Rollback

- **S0-04 only.** `20261105000004.README.md`, step 7, has the rollback SQL. It restores the dropped policies from `rls_migration_audit.s004_dropped_policies` and removes the `s004_%` policies. It reopens DB-02 while it is in place.
- **S0-03, S0-05, S0-06, S0-08, S0-10.** Their READMEs contain no rollback SQL. The only recovery is the restore point from step 1. Some changes are not reversible by SQL: S0-03 drops the security-answer and legacy-2FA columns, and S0-05 drops the RPCs. Their data is gone unless the restore point has it.

## Known risks

1. **S0-03 date comparison (fixed in source).** `20261105000003_lock_tenant_key.sql` compared `p.date_of_birth` with a `date` parameter in `patient_claim_candidates`. On a text column this fails with `operator does not exist: text = date`. The source now calls `patient_dob_as_date()`, which has a text overload (NULL, not YYYY-MM-DD and impossible dates give NULL, so no error and no match) and a DATE overload. The comparison works for either column type. Two facts to keep in mind: `src/integrations/supabase/types.ts` shows `string` for `date`, `timestamptz` and `text` alike, so it cannot tell the live type; and the repository migrations declare `patients.date_of_birth DATE NOT NULL`. Validated on a text-typed and a date-typed fixture.
2. **Live schema not captured.** Everything here was written from repo files and the generated types. The S0-01 baseline and the `live_*.tsv` captures do not exist yet. Column types, policy names and RLS state may differ on the live database. Part 04 is the most sensitive to this.
3. **S0-04 abort guard stops part 04 on the validation fixture.** Abort is the default. On the fixture, part 04 raised `role_aware_rls: ABORTED, nothing changed. 64 policy name(s) ... not in the reviewed list`. Nothing changed: the schema dump before and after the aborted part is identical except for pg_dump's random `\restrict` tokens, and `rls_migration_audit` was never created. The 64 names are listed in `20261105000004.README.md`, step 3. 63 of them are not in the repository history. `Staff can view prescriptions in their hospital` is in `supabase/migrations` but missing from the reviewed list for `prescriptions`. The live count will differ. Sweep mode, which would drop all 64, is not used in this bundle.
4. **S0-04 is not idempotent.** A second full run adds `s004_active_principal_guard` (RESTRICTIVE) on `lab_qc_results` and `lab_trends`. The cause: the guard applies only to tables that already have someone else's permissive policy, and S0-06 creates those policies after S0-04 runs. The added guard only narrows access to active staff. Found with a `pg_dump` diff of the schema after two full runs. Fixing it means changing the source. Not re-measured on this bundle, because part 04 does not complete on the fixture.
5. **Parts 05 and 06 are not transactions.** Part 04 is one transaction, guard included. A failure in part 05 or 06 leaves S0-04 partly applied. Recovery is the restore point, or the rollback in S0-04's README.
6. **Session-local helpers.** S0-04 defines `pg_temp.s004_staff` and `pg_temp.s004_self` and uses them later. Parts run in separate sessions, so the generator copies those two definitions into parts 05 and 06 as labelled "session prelude" blocks. The copies are verbatim source text. Validated on PostgreSQL 16.
7. **Editor transaction behaviour is unknown.** If the Lovable editor wraps each paste in its own transaction, a `BEGIN;` inside a wrapped part is a warning and its `COMMIT;` ends the editor's transaction early. Check the first wrapped part's result before continuing.
8. **Verify checks shape, not behaviour.** `99-verify.sql` checks that objects exist, RLS is on, the trigger exists, the signature matches, and the columns are gone. It does not check who can read what. The behaviour matrices in `tests/s0-03`, `tests/s0-04` (576 checks), `tests/s0-05`, `tests/s0-06-rls` and `tests/s0-10` have not been run against this bundle.
9. **Validation fixture is a stand-in.** It is the union of the test fixtures plus the `types.ts` tables. Its `auth.users` rows are the few the s0-04 fixture inserts, not real Supabase Auth. It has no pg_cron, pg_net or Vault, and no Supabase policies beyond the fixture's. It is not committed to the repository.
10. **Lab screens.** Part 08 makes six lab tables deny-by-default. `20261105000006.README.md` lists existing client issues it does not fix, including `calculateTrend` inserting `hospital_id: 'current'`, which is not a UUID.
11. **Secrets are not in the bundle.** The pepper, the Vault secrets, the edge-function secrets and the Auth settings are operator steps in the migration READMEs. Part 02 and part 01's worker need them.

## Validation

Generated with `node scripts/db/build-consolidated.mjs`. Validation ran on a scratch PostgreSQL 16.15 cluster (not a live database). Sequence: the compat shim, the union fixture (Known risks, item 9), each part in name order with `ON_ERROR_STOP=1`, then `00-preflight.sql` and `99-verify.sql`; then a second pass of all parts on the same database.

- **Text-typed fixture** (`patients.date_of_birth text`, as in `types.ts`). Run 1: part-01, part-02 and part-03 exit 0; part-04 exits 3 (the guard, 64 names). Run 2 (all parts again, same database): part-01 to part-03 exit 0, part-04 exits 3 again, and the schema is unchanged across part 04. Verify does not run after a stopped bundle. The read-only verify of the partial state, run for information only, gives 53 `ok` and 36 `MISSING`; every `MISSING` row belongs to parts 04 to 08.
- **Date-typed fixture** (`patients.date_of_birth date`). Run 1 only: the same result as the text-typed fixture (parts 01 to 03 exit 0, part 04 exits 3 on the same 64 names).

Repeat the same steps after any change to the source or the generator. The bundle is not validated end to end until the S0-04 names are reviewed and the guard passes.
