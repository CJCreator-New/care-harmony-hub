# 20261105000007: state machines for prescriptions and discharge

Roadmap S1-02. Issues DB-10, CLIN-11 and CLIN-20 are addressed in part; CLIN-17
is not (see "Not covered"). The migration
`20261105000007_state_machines.sql` adds BEFORE UPDATE triggers that refuse
illegal state changes, so a direct REST call fails the same way the edge
function does. Nothing has been applied to any database.

The rule for each transition is the union of what the code really does and
what ADR-0003 and ADR-0004 require:

- Where an ADR forbids a jump, the database refuses it, even if some client path
  makes it. ADR-0004 forbids `initiated` or `pending_approval` to `dispensed`.
- Where the code does something the ADRs are silent on, the database allows it.
  Examples: the AMA discharge, the `partially_dispensed` state and the client's
  clarification and cancel paths.

## What is enforced

### `prescription_approval_workflows` (ADR-0004)

| From | To | Action (where the code does it) | End-user role (JWT) |
|---|---|---|---|
| initiated, pending_clarification | pending_approval | review | pharmacist |
| pending_approval, pending_clarification | approved | approve | pharmacist |
| initiated, pending_approval | pending_clarification | clarify | pharmacist |
| initiated, pending_approval, pending_clarification, approved | rejected | reject | pharmacist |
| approved | dispensed, partially_dispensed | dispense | nurse, pharmacist, doctor, admin |
| partially_dispensed | dispensed | dispense | nurse, pharmacist, doctor, admin |
| dispensed, partially_dispensed | completed | complete | nurse, pharmacist, doctor, admin |
| initiated, pending_approval, pending_clarification, approved | cancelled | cancel | nurse, pharmacist, doctor, admin |

- `completed`, `rejected` and `cancelled` are terminal.
- `initiated` or `pending_approval` to `dispensed` is refused, as ADR-0004 requires.
- The status CHECK gains `partially_dispensed`, which the client writes.

### `discharge_workflows` (ADR-0003)

`current_step` and `status` are checked together. Each edge sets one status.

| From step | To step | Status set | End-user role (JWT) |
|---|---|---|---|
| pharmacist | billing | in_progress | pharmacist (approve) |
| billing | nurse | in_progress | receptionist, admin (approve) |
| nurse | completed | completed | nurse (approve) |
| pharmacist | doctor | in_progress | pharmacist (administrative reject) |
| billing | pharmacist, doctor | in_progress | receptionist, admin (reject; doctor is clinical) |
| nurse | billing, doctor | in_progress | nurse (reject; doctor is clinical) |
| doctor, pharmacist, billing, nurse | completed_ama | completed_ama | doctor, admin (AMA) |
| doctor, pharmacist, billing, nurse | cancelled | cancelled | admin, or the doctor who initiated it |

- `completed`, `completed_ama` and `cancelled` are terminal.
- The status CHECK and the current_step CHECK gain `completed_ama`. Before this
  file, the AMA path (`discharge-workflow/index.ts`, `dischargeAMAWorkflow`)
  wrote a value the CHECK refused, so AMA never succeeded.

### `prescriptions.status` (ADR-0004, client writes)

| From | To | End-user role (JWT) |
|---|---|---|
| pending, pending_clarification | verified | pharmacist |
| pending | pending_clarification | pharmacist |
| verified | dispensed, partially_dispensed | no DB role rule (see below) |
| partially_dispensed | dispensed | no DB role rule (see below) |

Direct `pending` to `dispensed` or `partially_dispensed` is refused (ADR-0004).
`prescriptions.status` has no CHECK constraint, so the trigger is the only guard
on it. Values the code never writes are refused as targets.

### Role rule and service role

The role check applies only when the JWT role is `authenticated` or `anon`. For
those callers `sm_caller_has_role` requires an active user (profile not
deactivated, `user_roles` row in the same hospital). The service role, the
table owner and SQL-editor sessions skip the role check and keep the transition
rule. The edge functions run as service role, so this does not change their
behavior. The role checks in `discharge-workflow/index.ts` and
`prescription-approval/index.ts` still run first.

## Findings: code paths that violate or dead-end the state machine

These are not changed by this migration. Each needs a decision in the code or
in the ADR.

1. **Client creates approval workflows already at `pending_approval`.**
   `src/modules/prescription-dispensing/PrescriptionDispensingEngine.ts:64`
   inserts `status: 'pending_approval'` and `current_step: 2`. ADR-0004 starts
   at `initiated`. A trigger on UPDATE does not see INSERTs, so this path is not
   blocked. The row also skips `review`.
2. **Client allows admin to approve, reject, clarify and review; ADR-0004 and the
   edge function allow only the pharmacist.** `core/stateMachine.ts:66`. The DB
   follows ADR-0004 and the edge function, so an admin's client-side approve
   fails with `SM_ROLE_FORBIDDEN`. A product decision is needed: either the
   client drops admin or the ADR and the DB rule change.
3. **Client dispense can run from `pending`.**
   `src/lib/hooks/pharmacy/usePrescriptions.ts` around line 587 writes
   `dispensed`/`partially_dispensed` with no precondition on the current status.
   After this migration, that call fails with `SM_ILLEGAL_TRANSITION` unless the
   prescription is `verified` first. The UI gate must check this.
4. **Clinical rejection to `doctor` is a dead end.**
   `discharge-workflow/index.ts` (`rejectWorkflow`, clinical branch, lines
   ~414-416) moves the workflow to `doctor`. `approveWorkflow` (`NEXT_STEP` has no
   `doctor` key) and `rejectWorkflow` (`PREVIOUS_STEP` has no `doctor` key) both
   refuse it. Only AMA or cancel can leave `doctor`. This is CLIN-11. The DB
   allows the rollback and no exit from `doctor`. A resubmit edge (for example
   `doctor` to `pharmacist`) is a product decision and is not added here.
5. **Cancel has no terminal guard in the code.** `cancelWorkflow` updates by id
   and current_step only. The DB now refuses cancel from `completed`,
   `completed_ama` and `cancelled`, including from the service role.
6. **Discharge is initiated at `pharmacist`, not `doctor`.**
   `initiateWorkflow` inserts `current_step: 'pharmacist'` (line ~224), and the
   audit row says `fromStep: 'doctor'`. ADR-0003 starts at `doctor`. Not blocked
   by the DB (INSERT).
7. **Approval edge function: `pending_clarification` has no exit.**
   `getNextState` (lines 84-99) allows `review` only from `initiated`, and
   `approve`/`reject` only from `pending_approval`. The `ALLOWED_TRANSITIONS`
   constant (line 59) suggests `pending_clarification` to `pending_approval` was
   intended but is unused. The DB allows `pending_clarification` to
   `pending_approval` and to `approved` (client path), so the DB is wider than the
   edge function here.
8. **Client clarify, reject and cancel accept any non-terminal status.**
   `core/stateMachine.ts` has no status precondition for `clarify`, `reject` or
   `cancel`. The DB restricts clarify to `initiated`/`pending_approval`, and
   reject and cancel to states before dispensing. The client can therefore offer
   actions the DB refuses (for example clarify after `approved`).
9. **Direct REST writes to the approval table.** The pharmacist UPDATE policy in
   `20260325_create_prescription_approval_workflows.sql` and the client's
   `save()` (`src/modules/prescription-dispensing/adapters/SupabasePrescriptionAdapter.ts`,
   `.upsert(workflow)`) let a pharmacist write `status` directly. The trigger now
   applies to those writes, so the DB rule is what constrains the client path.
10. **Dispense has no DB role rule for `prescriptions`.** The client grants the
    dispense permission by `prescriptions:write`, and the set of roles is not
    confirmed. The DB only checks the transition (see the table above).

## CLIN-20: amendment RPC (not fixed here)

`src/components/audit/AmendmentModal.tsx` calls `amend_prescription_dosage` with
eight named parameters (`p_old_quantity`, `p_new_quantity`,
`p_amendment_justification`, `p_amending_doctor_id` and others). The function
created in `20260313000002_prescription_approval_logging_triggers.sql` (line 233)
takes five parameters. PostgREST cannot resolve the call, so it fails every
time. The roadmap wants the signature fixed, and the design (see the issue) would
orphan the order. Both need a decision, so this migration does not change the
function.

## Not covered

- **CLIN-17** (lab specimen rejection violates the status CHECK on lab orders,
  and sample tracking is disconnected from orders): not investigated in this
  pass. It needs its own migration, and it is out of scope for this file.
- `prescription_items`: no state machine (only `is_dispensed`), so not touched.
- `prescriptions.status` has no CHECK constraint. Adding one now would refuse the
  values the client already writes (`active`, `filled`, `received` and others
  used by other paths), so it is left to the trigger.

## Validation performed

- No live database. The full history (`supabase/migrations`) cannot be replayed
  on this machine: `scripts/db/replay-migrations.mjs` applies 10 of 64 files and
  creates 0 tables in `public`. This is the known S0-01 / DB-03 result, so the
  migration was tested on a stub base built from the real `CREATE TABLE`
  statements for `prescriptions` (`20260204000011_misc.sql`),
  `prescription_approval_workflows` (`20260325_...sql`), `discharge_workflows`
  (`20260311000003_patient_discharge_workflow.sql`) and the compat shim, on a
  local PostgreSQL 16 cluster.
- The migration applies, and applying it a second time is a no-op. All three
  triggers are enabled. The CHECKs and the SECURITY DEFINER functions with
  `search_path = ""` were inspected in the catalog.
- A transition matrix of 70 cases (25 approval, 30 discharge, 15 prescription)
  ran as pharmacist, nurse, doctor, admin, receptionist, deactivated pharmacist,
  other-tenant pharmacist and service role. Every case got the expected result.
  Every refusal is an `SM_ILLEGAL_TRANSITION`, `SM_ROLE_FORBIDDEN` or CHECK error,
  not a privilege error.
- Control run, same matrix on the base without the migration: 30 illegal
  transitions were accepted, including `initiated` to `dispensed`, a receptionist
  approving the pharmacist step, and cancel after completion. The AMA case was
  refused by the CHECK.
- Not run: `transition_discharge_workflow` RPC itself (it is an UPDATE, so the
  trigger applies), and the edge functions end to end.

## Promoting this file

1. Confirm the prerequisites exist in the captured live baseline. The guard in
   the file checks the tables, columns and `auth.uid()` and `auth.role()`, and
   aborts without changes if one is missing.
2. Replay it on the baseline. It must exit 0, and a second run must also exit 0.
   The script is `scripts/db/replay-migrations.mjs` after S0-01.
3. Give it a version after the baseline, `git mv` it into `supabase/migrations/`,
   and open a PR. Regenerate `src/integrations/supabase/types.ts` (the CHECK
   values changed).
4. Before the migration goes live, decide findings 1-4 and 10 above. Otherwise
   the AMA path works, but the client's admin approve and the dispense-from-pending
   path fail.
