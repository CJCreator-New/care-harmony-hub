# Two-factor authentication: Supabase Auth MFA (S0-10, client side)

Roadmap item S0-10 (ARCH-06, EDGE-05, SECF-01, SECF-02, EDGE-12) replaces the custom
TOTP implementation with Supabase Auth MFA TOTP factors. This page covers what the
client now does, the migration for existing users, and what still has to happen on
the server.

## What changed in the client

| Area | Before | Now |
|---|---|---|
| Secret and QR | Generated in the browser with `Math.random` (`src/lib/hooks/auth/useTwoFactorAuth.ts`) or by `generate-2fa-secret` (not valid base32) | Generated by Supabase Auth: `supabase.auth.mfa.enroll({ factorType: 'totp' })` |
| Enrolment counts when | `store-2fa-secret` was called; no proof of the code was needed | `mfa.challenge` + `mfa.verify` succeed with a code from the app. Unverified factors are removed on cancel, retry and unmount |
| Login | Full session, then an optional modal that checked `profiles.two_factor_enabled` (failed open on error) | Password sign-in gives an `aal1` session. The route guard sends any user with a verified factor to `/hospital/mfa-challenge` until `mfa.verify` upgrades the session to `aal2` |
| Lookup errors | Treated as "2FA not required" | Treated as "challenge required": the user stays on the challenge page with Retry / Sign out |
| Mandatory enrolment (admin, doctor) | Checked on 5 non-PHI routes only | Checked by the shared `ProtectedRoute`, which now wraps every role-protected route (`withRoleAccess`) |
| Source of truth | `profiles.two_factor_enabled` (self-writable) | Supabase Auth factors and the JWT `aal` claim. `two_factor_enabled` is ignored |

Code: `src/lib/auth/mfa.ts` (service and decision table), `src/lib/hooks/auth/useMfaAssurance.ts`
(shared per-token lookup), `src/routes/routeDefinitions.tsx` (guards),
`src/components/auth/TwoFactorSetup.tsx`, `src/pages/hospital/MandatoryTwoFactorSetupPage.tsx`,
`src/pages/hospital/MfaChallengePage.tsx`.

Guard decision (`resolveMfaGate`):

| Assurance lookup | Verified TOTP factor | Session `aal` | Role requires 2FA | Result |
|---|---|---|---|---|
| pending | - | - | - | spinner, nothing rendered |
| error | - | - | - | challenge page (fail closed) |
| ok | yes | aal2 | any | allow |
| ok | yes | aal1 | any | challenge page |
| ok | no | any | yes (admin/doctor, or `profiles.two_factor_required`) | enrolment page |
| ok | no | any | no | allow |

The lookup (`mfa.getAuthenticatorAssuranceLevel` + `mfa.listFactors`) runs once per access
token. When the token is refreshed within the same Supabase session (same JWT
`session_id`), the previous result is served during the re-check, and a failed re-check
keeps it, so an hourly refresh does not unmount the page in use. A new sign-in has a new
`session_id` and always starts from "pending".

The mandatory roles mirror `public.role_requires_2fa()` in
`supabase/migrations/20260622000001_enforce_2fa_for_clinical_roles.sql`.

## Migration for existing users

No data is migrated. Secrets in `two_factor_secrets` cannot be imported into Supabase
Auth, and they were generated with a weak RNG or a non-base32 alphabet anyway.

- **Admin and doctor accounts** (including those that had enabled the old 2FA): at the
  next login they are sent to `/hospital/two-factor-setup` and must scan a new QR code
  and confirm a code before any app route renders. The page tells them that the old
  authenticator entry can be deleted from their app.
- **Other roles that had enabled the old 2FA**: they are not challenged, because they
  have no Supabase factor. They can enrol again from Profile → Security. Tell these
  users in the release note.
- `profiles.two_factor_enabled` is no longer read or written by the client. It stays in
  the database for the server-side clean-up below.

Suggested release note: "We have upgraded two-factor sign-in. Administrators and doctors
will be asked to set up their authenticator app again at their next sign-in. Your old
backup codes still work for one-time recovery until new ones are issued."

## Backup codes

The "Use a backup code" link on the challenge page calls the `verify-backup-code` edge
function with `{ code }` and expects `{ success: boolean }`. That function is being
reworked server-side so that on success it consumes the code atomically and unenrols the
user's TOTP factor. The client then signs out locally (`signOut({ scope: 'local' })`) and
returns to the login page with a notice. After signing in again the user has no factor;
an admin or doctor is sent to enrol a new one and ends at `aal2`.

New enrolments do not issue backup codes. Supabase Auth MFA has no backup codes, so
issuing new ones is part of the server-side rework.

## Still required on the server (not in this change)

1. **Confirm TOTP MFA is enabled** in the Supabase project: Dashboard → Authentication →
   Multi-Factor (hosted projects normally have TOTP on by default). For the local stack,
   `supabase/config.toml` has no `[auth.mfa.totp]` section yet; add `enroll_enabled = true`
   and `verify_enabled = true` there. If TOTP is off, `mfa.enroll` fails, and admin/doctor
   accounts cannot get past the enrolment page.
2. **Enforce `aal2` in RLS** for privileged roles: `(auth.jwt()->>'aal') = 'aal2'` on PHI
   policies, and the same check in the edge functions. Until then the guard is a client
   control only: a stolen password plus a direct REST call still reaches PHI at `aal1`.
3. Rework `verify-backup-code` as described above, and issue server-generated codes.
4. Retire `generate-2fa-secret`, `store-2fa-secret`, `verify-2fa` and `verify-totp`. The
   client no longer calls them. Then drop `two_factor_secrets` and stop the self-service
   writes to `profiles.two_factor_*`.
5. The admin staff list (`adminUserManagementService`) still shows the legacy
   `two_factor_enabled` flag. Derive it from `auth.mfa_factors` server-side.

## How to verify on a live project

1. In the Dashboard, check Authentication → Multi-Factor: TOTP enrolment and verification
   are enabled.
2. Sign in as a doctor with no factor. You land on `/hospital/two-factor-setup`. Type
   `/patients` in the address bar: you are sent back to the enrolment page.
3. Scan the QR code, enter a code and confirm. You reach `/dashboard`. In the browser
   console, decode the access token: `aal` is `aal2`. Under Authentication → Users → the
   user, one verified TOTP factor is listed.
4. Sign out and in again. You land on `/hospital/mfa-challenge`. Try `/patients`: you are
   sent back to the challenge page. Enter a code: you reach the app.
5. Start an enrolment from Profile, close the dialog, then check the user in the
   Dashboard: no unverified factor is left behind.
